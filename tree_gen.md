# tree_gen.md — Plan: batched, bit-for-bit replication of ysagiv tree construction

**Status:** planning only. No subagent deployed yet. This document (a) describes
exactly how the canonical `ysagiv` `human_trees` are constructed today, (b)
profiles that tree set and infers the binding search parameters, (c) establishes
*why* a bit-for-bit speedup is even possible, and (d) specifies the batched
generator and the test suite that must guard it. The last section is the brief
the subagent will execute.

Related: [[tree-set-and-gss]] (which tree set is canonical, join-by-FEN),
[[fens-unification-plan]] (the FEN universe and `process_fens.py`).

## 0. TL;DR of the key findings

- The canonical trees at `/scratch/gpfs/GRIFFITHS/ysagiv/chess/CTS/data/human_trees`
  (181,992 `*.pt` files, format `cts_raw_pretrain_example_v5`) were generated by
  **this repository's `cts` package** (`cts.data.build_tree generate-dataset` →
  `build_pretrain_example` → `generate_partial_tree_from_provider`). Every
  metadata tag matches the constants hard-coded in
  [build_tree.py](lmcos/src/data/build_tree.py): `search_config_id =
  supervised_branch_v1`, `edge_wdl_target_generation_version =
  search_consolidated_edge_wdl_v1`, `oracle_trace_generation_version =
  generated_search_root_q_v1`, `provider_metadata = {engine_kind: lc0,
  value_source: valuehead, prior_source: classic_nodes_1}`.
- **The expansion budget is a constant 96** (`search_budget = min_nodes =
  max_nodes = 96`). All 250 sampled trees have exactly 96 oracle-trace rows
  (= 96 expansions). Because `NodeBudgetDistribution.sample` short-circuits when
  `min_nodes == max_nodes`, **no RNG is ever drawn** during generation under this
  config. PUCT itself is deterministic. **Therefore the only thing that can make
  two generation runs differ is the lc0 neural-net evaluation.** This is the
  crux: bit-for-bit replication reduces entirely to "make/keep the engine evals
  identical."
- **`max_depth = 36`, and it is non-binding.** The committed configs say
  `max_depth: 4`, but the canonical trees reach far deeper, so that value was not
  used. The value actually used is believed to be **36**. A 1,500-tree scan
  confirms 36 is never reached or even approached: global max depth is **22**,
  nothing is within 14 plies of 36, and the tail tapers smoothly (no pile-up).
  So for replication the cap never binds — any cap ≥ ~23 yields identical trees —
  but we set it to 36 to match the believed config. See §2.

**Two-track validation (per the directives driving this plan):**
- **Track A — our-own ref-vs-batched (primary correctness).** Generate our own
  trees with the *unchanged* code (reference) and with the batched change, on the
  same machine/backend/weights at `max_depth = 36`, and compare. This gives a
  clean **exact-equality** bar *and* a head-to-head speed profile, and it
  sidesteps the backend-mixing and run-to-run-determinism caveats that make
  comparing against ysagiv's *stored* bits unreliable.
- **Track B — ysagiv proxy at depth-36.** Re-run a few real ysagiv root FENs at
  `max_depth = 36` and confirm 36 is non-limiting (the tree never hits the cap),
  using the corpus as a sanity proxy rather than a bitwise oracle.

## 1. How trees are generated today (the protocol, in full)

### 1.1 Entry point and the two lc0 engines

`cts.data.build_tree generate-dataset`
([build_tree.py:276](lmcos/src/data/build_tree.py#L276)) loads the root FENs,
slices the shard range, and constructs **two** long-lived lc0 subprocesses
wrapped in one `Lc0DirectEvalProvider`:

| engine | mode | search limit | options | role |
|--------|------|--------------|---------|------|
| **prior** | `classic` | `go nodes 1` | `multipv 8`, `VerboseMoveStats true` | per-move priors (policy head) from `verbose-move-stats` |
| **value** | `valuehead` | `go nodes 1` | `UCI_ShowWDL true` | the position's own WDL (value head) |

Both run with the same weights file
(`t1-256x10-distilled-swa-2432500.pb.gz`). `nodes=1` means "one node of search"
= a single NN forward pass; there is no tree search inside lc0. The two-engine
split exists because the prior needs `classic` + multipv to surface sibling
priors, while the value head needs `valuehead` mode + `UCI_ShowWDL`.

The UCI transport is one synchronous round-trip per position
([process.py `analyse`](lmcos/src/core/providers/process.py#L141)): write
`position …` + `go …`, read lines until `bestmove`. **One position per `go`.
This is the bottleneck** — at `nodes=1` the GPU does a batch-of-1 forward pass
and then blocks on a stdin/stdout round-trip.

### 1.2 The provider contract

`Lc0DirectEvalProvider`
([lc0.py](lmcos/src/core/providers/lc0.py)) exposes:

- `root_features(fen)` → `{wdl_*, value, prior: 1.0}` for the root (value-engine
  read, or synthesized for a terminal root).
- `expand_node(fen, depth)` → one `ExpansionChild` per legal move: the prior
  engine enumerates moves + priors (one prior `analyse` on the **parent**), then
  for **each non-terminal child** a value `analyse` is run for its WDL. Terminal
  children short-circuit (no value call).
- Three per-FEN caches (prior / value / terminal). Caches persist across roots
  and are flushed every `cache_clear_interval = 128` roots. **Caches only affect
  speed, never values** (a FEN maps to one deterministic eval), so they are
  irrelevant to bit-for-bit identity but must be respected so the batched path
  doesn't accidentally diverge on transpositions.

Per expansion the engine cost is therefore: **1 prior eval (parent) + ~K value
evals (children)**, where K ≈ 25 (median root branching; see §2). The value
evals dominate and are embarrassingly parallel.

### 1.3 The PUCT generation loop (the thing we must replicate exactly)

`generate_partial_tree_from_provider`
([teacher_targets.py:1344](lmcos/src/data/preprocess_gnn/teacher_targets.py#L1344)):

1. `sampled_node_budget = node_budget_distribution.sample(rng)`. **With
   `min==max==96` this returns 96 and consumes no RNG** (short-circuit at
   [teacher_targets.py:94](lmcos/src/data/preprocess_gnn/teacher_targets.py#L94)).
2. Initialize the tree with the root only; `root_features` is read from the
   value engine.
3. **Simulation loop** while `num_expansions < 96` and an expandable frontier
   exists (capped at `max_simulations = budget * 50`):
   - `_select_leaf_by_puct` walks root→leaf taking the argmax of
     `Q(child) + c_puct · P(child) · sqrt(ΣN)/(1+N_child)`
     ([teacher_targets.py:1176](lmcos/src/data/preprocess_gnn/teacher_targets.py#L1176)).
     `c_puct = 1.0`. Tie-break is **strict `>`**, i.e. first child in
     `tree.child_ids` order wins — deterministic.
   - If the leaf is terminal or at `max_depth`: mark terminal, backprop its
     **static** value (already on the node, no engine call), `continue` — this
     does **not** increment `num_expansions`.
   - Else `provider.expand_node` → `_prepare_children` normalizes priors
     (`normalize_prior_scores`) → `add_children` → init `EdgeStats` →
     `num_expansions += 1` → `_backpropagate_path` (negate value + swap W/L WDL
     each ply up) → `_record_oracle_root_trace` (snapshot root per-move Q +
     argmax + visits).
4. `consolidate_generated_tree` → per-node value targets = visit-weighted mean
   child Q (`_backup_target_from_child_q`); per-edge WDL targets = visit-mean
   WDL or static fallback (`_edge_target_wdls_from_edge_stats`).

The on-disk record (`RawPretrainExampleRecord`) stores children in **UCI-sorted
slot order** (`_child_ptr_and_children_index`), a dense NaN-filled feature
matrix, CSR `child_ptr`/`children_index`, the oracle trace, and (compactly) the
root FEN when child FENs are reconstructable by replaying moves.

### 1.4 Where determinism lives — and the single risk

Deterministic, order-independent, RNG-free under the canonical config:
`NodeBudgetDistribution` (constant 96), PUCT selection (strict argmax),
prior normalization, backprop arithmetic, target consolidation, UCI-sorted
serialization.

**The one and only divergence risk is the lc0 NN evaluation.** Two sub-points:

- *Backend.* The canonical corpus uses the **cuda lane only** (the committed
  50K base file also defines a `blas` lane, but the corpus we treat as canonical
  was generated on cuda). So the corpus is internally consistent on one backend,
  and "bit-for-bit" is defined **relative to cuda + these weights**. The open
  risk is therefore not backend *mixing* but cuda *run-to-run* reproducibility
  (§5.3): GPU kernels can be nondeterministic even at batch 1, which would cap
  how "exact" any comparison — stored or freshly regenerated — can be.
- *Batch invariance.* If the batched path evaluates many positions in one NN
  forward pass, GPU kernel/reduction-order effects can perturb low-order bits
  versus a batch-of-1 eval. Whether lc0 is batch-invariant for a given backend
  is an **empirical question the test suite must answer** (§4.1) before any
  batched NN path is trusted.

## 2. Profile of the canonical `human_trees` (and inferring `max_depth`)

Source: `/scratch/gpfs/GRIFFITHS/ysagiv/chess/CTS/data/human_trees`,
**181,992** files, all format `cts_raw_pretrain_example_v5`. Random sample of
250 trees (seed 1):

| quantity | min | median | max |
|----------|-----|--------|-----|
| **num_expansions** (oracle-trace rows) | 96 | 96 | 96 |
| max node depth | 3 | 7 | **18** |
| node count | 739 | 2572 | 4503 |
| root branching (root children) | 1 | 25 | 52 |

Depth distribution (n=250):
`{3:2, 4:28, 5:41, 6:55, 7:59, 8:24, 9:17, 10:8, 11:5, 12:4, 13:2, 14:3, 16:1, 18:1}`.

A larger 1,500-tree scan (seed 7) extends the tail but tells the same story:
**global max depth = 22**, zero trees at depth ≥ 30 (let alone ≥ 36), only
0.47% at depth ≥ 18, and **all 1,500 have exactly 96 expansions**. Deep tail:
`{12:21, 13:11, 14:6, 15:4, 16:3, 17:1, 19:2, 20:1, 21:1, 22:3}`.

### 2.1 Budget is a hard constant

Every sampled tree has exactly 96 expansions ⇒ `search_budget = min_nodes =
max_nodes = 96`. This is what zeroes out the RNG. **The batched generator must
assert this** (it relies on the no-RNG property; a log-uniform budget range would
reintroduce an ordering dependency — see §3.4).

### 2.2 `max_depth = 36`, non-binding

The committed `max_depth: 4` cannot be the value used: a depth-4 cap makes depth
5 impossible, yet we observe depth up to 22. The value believed to have been used
is **36**, and the data confirm it is **never limiting**: across 1,500 trees the
deepest line is 22 plies — 14 short of the cap — and the histogram tapers
smoothly with no pile-up (the signature of a cap that is never reached).

**For replication this is benign:** as long as `max_depth` ≥ the deepest line any
tree reaches within 96 expansions, its exact value changes no output bit. Since
nothing reaches ~23, **36 is bit-equivalent to any larger cap** and to the
believed ysagiv config. We set the batched generator to `max_depth = 36`.

### 2.3 Work item — confirm non-binding at scale (cheap)

The 1,500-tree sample already settles this (max depth 22, all 96 expansions), and
each `torch.load` is ~3 ms so a full 181,992-tree pass is ~10 min if we ever want
the exact global maximum. Not a blocker — the design does not depend on the
precise cap, only on it being ≥ ~23. Track B (§0) re-derives the same conclusion
directly from generation: run a few ysagiv roots at `max_depth = 36` and assert no
node is marked terminal *by the depth cap*.

## 3. Design: batched "walk-the-trees-together" generator

### 3.1 Principle

Within a single tree, expansions are strictly sequential — expansion *k+1*'s PUCT
path depends on *k*'s backprop. **Across trees they are independent.** So we keep
a pool of `B` trees in flight and advance them in lock-step over *simulations*,
batching the engine evals that the simulations request. Each tree keeps its own
`SearchTree` + `edge_stats` and reuses the **exact** sequential math
(`_select_leaf_by_puct`, `_prepare_children`, `add_children`,
`_backpropagate_path`, `_record_oracle_root_trace`, `consolidate_generated_tree`).
Nothing in the search logic is rewritten — only *when/how the evals are
dispatched* changes.

### 3.2 The lock-step schedule

The sequential loop counts *expansions*, but some simulations select a
terminal/depth-capped leaf and resolve with no engine call. So lock-step is over
**simulations**, not expansions, and trees finish at different rounds:

```
active = pool of B trees, each at num_expansions = 0
while active:
  # ---- selection (pure CPU, per tree) ----
  for t in active:
      leaf, path = _select_leaf_by_puct(t.tree, t.edge_stats, cfg)
      if leaf is terminal or depth-capped:
          backprop static value; record nothing  # no eval; does not consume budget
      else:
          mark t as "needs prior eval on leaf.fen"
  # ---- phase A: ONE batched prior eval over all distinct leaf FENs ----
  prior_results = batched_prior_eval([t.leaf.fen for t in needing_prior])
  # ---- phase B: ONE batched value eval over all distinct child FENs ----
  child_fens = union of non-terminal children discovered in phase A
  value_results = batched_value_eval(child_fens)
  # ---- apply (pure CPU, per tree, EXACT sequential order within a tree) ----
  for t in needing_prior:
      children = assemble ExpansionChild list from prior_results + value_results
      _prepare_children(...); add_children; init EdgeStats
      t.num_expansions += 1; _backpropagate_path(...); _record_oracle_root_trace()
      if t.num_expansions == 96 or no expandable frontier: move t out of active
```

A shared FEN→result cache spans the whole pool (a transposition evaluated for one
tree serves all). Because a FEN deterministically maps to one eval, the shared
cache cannot change outputs — it only removes redundant work, and it makes the
batched run match the sequential run on transpositions.

### 3.3 The batched eval — single process, one batched forward pass (corrected design)

> **Course correction (2026-06-18).** The first attempt (see §3.5) batched trees
> *logically* but still sent every position to lc0 **through UCI, one `go` per
> position**, so the "batch" never reached the GPU as a batch — it was the same
> N batch-of-1 forward passes, reordered, hence **1.0x**. Its only lever for
> speed was running *multiple engine processes* to hide UCI latency, which (a) was
> *slower* at this scale (orchestration + one GPU contended by many processes) and
> (b) introduced ~1e-2 divergence from per-process cuDNN kernel autotuning. Both
> pathologies are artifacts of multi-process UCI plumbing, **not** of batching.

**The right design (what we build now):** one process, one loaded network, and at
each lock-step step concatenate **all the frontier positions across the N trees
into a single batched forward pass** on one GPU. This is exactly how lc0's own
MCTS evaluates leaves (it gathers a minibatch and calls the backend's
`ComputeBlocking` once); UCI `nodes=1` is just the degenerate batch-of-1 case of
that same path. So:

- **Speed.** A GPU forward over a batch of N positions costs ≈ the same wall-clock
  as a batch of 1 (the batch dimension is what the GPU parallelizes). N sequential
  batch-1 passes → one batch-N pass. This is the actual order-of-magnitude win and
  directly addresses "we're not parallelizing Lc0 over the tree."
- **Cleanliness.** One process, one network instance ⇒ no cross-process kernel
  autotuning ⇒ the ~1e-2 divergence of §3.5 does not arise.

**Mechanism.** Bypass UCI; call lc0's backend eval directly via its
`NetworkComputation`-style batched API. Candidate access paths (subagent picks the
fastest that works): lc0 python bindings under `src/python`; a minimal C++ tool
linking `liblc0`; or extending the fork. Two engineering requirements for
bit-faithfulness to the existing protocol:

1. **Two heads, two paths.** Priors today come from `classic`+`VerboseMoveStats`
   (policy head, post-processed: softmax/temperature + legal-move masking),
   values from `valuehead` (WDL head). The batched evaluator must reproduce *both*
   transforms so its priors match the parsed `(P: %)` numbers and its WDL matches
   the valuehead output. Same network, but the post-processing must be replicated
   exactly (or proven equal).
2. **Independence along the batch dim.** A feedforward conv net does no
   cross-position mixing, so batch-N and batch-1 compute the *identical
   mathematical function* per position. Any difference is purely floating-point
   (cuDNN may pick a different algorithm for a different batch shape). Expected to
   be exact or ~1e-6, **not** the ~1e-2 cross-process effect — but it must be
   measured (§4.1) and, if nonzero, pinned (deterministic algorithms / disable
   TF32) per the §5b determinism decision.

### 3.4 Lock-step note (revised for true batching)

The §3.2 schedule still holds, with the eval phases now meaning **one GPU
forward pass each** (not a logical group of UCI calls): phase A = batched policy
eval over all distinct frontier-leaf FENs; phase B = batched WDL eval over all
distinct child FENs discovered in A. The per-tree CPU work (PUCT select, prepare,
add_children, backprop, oracle trace) is unchanged and reuses the existing
functions verbatim. The shared FEN cache still spans the pool.

### 3.5 What the first agent built (abandoned, kept for reference)

Worktree `agent-a6533d7351286cefd` contains a UCI-based lock-step driver
(`lmcos/src/data/batched_tree_gen.py`) + a bit-exact test harness
(`lmcos/tests/test_batched_tree_gen_bitexact.py`) + determinism/speed probes
under `lmcos/tools/batched_tree_gen/`. **It is not the design above** and is not
being merged. Useful takeaways carried forward: (i) single-process lc0 evals are
bit-deterministic and history-independent on cuda and eigen; (ii) *separate* cuda
processes diverge at ~1e-2 (kernel autotuning) — which is why the new design uses
exactly one process; (iii) the no-RNG / constant-budget precondition and the
`assert_records_bit_identical` field list are correct and reusable as a *spec*
(but the new test suite is written independently — see §6).

### 3.6 Invariants the generator must assert at startup

- `search_budget == min_nodes == max_nodes` (no-RNG precondition). Refuse to run
  a log-uniform budget through the batched path without an explicit
  ordering-preservation story (each tree's budget must be drawn from the shared
  RNG in exact global-index order, *before* any batching, to match the sequential
  RNG consumption).
- `c_puct`, `multipv`, `max_depth`, weights path, backend, engine mode, and all
  `provider_metadata` match the reference config.
- Output record schema/format byte-identical (`cts_raw_pretrain_example_v5`,
  UCI-sorted slots, compact position spec, oracle-trace tensors).

## 4. Test suite: prove bit-for-bit identity

A dedicated test module (e.g. `lmcos/tests/test_batched_tree_gen_bitexact.py`).
All smoke/integration cases **must time out after ~2 minutes** (`pytest.ini`
marker or an in-test `signal`/`pytest-timeout` of 120 s).

### 4.1 Within-process batch invariance (the gating test for the new design)

Single lc0 backend process, one loaded network: take ~50 FENs; for the policy
head and the WDL head, evaluate each FEN (a) alone (batch 1) and (b) inside a
batched forward pass of 256 (padded with unrelated FENs). Assert the target
position's outputs are **bitwise equal** between (a) and (b). Because positions
are independent along the batch dimension, equality is expected (or differences at
~1e-6); a larger gap means cuDNN is choosing a shape-dependent algorithm and we
must pin a deterministic one / disable TF32 (per §5b decision) and re-test. This
test decides whether the batched generator is bit-identical to a batch-1 backend
reference, so it runs **first**, before the generator is trusted.

### 4.2 Sequential-vs-batched equality (the core guarantee)

For a fixed small FEN set (~8–16 positions covering: high branching, near-mate,
a stalemate/checkmate root, a shallow tree, a deep-line tree), generate each tree
**twice under the same backend + weights**:
- (ref) `cts.data.build_tree` as it exists today, one tree at a time;
- (new) the batched generator with the same FENs in one pool.

Assert **exact equality** of every persisted field, loading via
`RawPretrainExampleRecord`:
`root_position_spec`, `incoming_moves`, `feature_names`, `node_features`
(bitwise, NaN-aware), `parent_index`, `child_ptr`, `children_index`, `depth`,
`is_terminal`, `is_expanded`, `node_targets`, `edge_wdl_targets`,
`oracle_trace_expansion_counts`, `oracle_root_moves`, `oracle_root_q_trace`,
`oracle_best_move_index`, `oracle_final_root_q_values`, `metadata`,
`sparse_node_metadata`. A helper `assert_records_bit_identical(a, b)` should do
exact `torch.equal` (with an explicit NaN==NaN clause for the dense feature
matrix and WDL targets) and structural equality on the python fields.

### 4.3 Order/pool-size invariance

The same FEN must yield the same tree regardless of (a) pool size `B`, (b) its
position within the batch, and (c) which other FENs share the pool. Generate one
FEN at `B=1`, `B=8`, `B=64` and in different pool compositions; assert all
records bit-identical. This catches accidental cross-tree state leakage (shared
mutable buffers, cache key collisions, batch-position-dependent floats sneaking
through).

### 4.4 ysagiv proxy at depth-36 (Track B — sanity, not a bitwise oracle)

The primary correctness bar is Track A (§4.2/§4.3): our-own reference vs batched,
same machine/backend/weights, which is **exact** by construction and immune to
backend mixing and cross-run nondeterminism. The canonical corpus is used only as
a *proxy*:
- Re-run the batched generator on a handful of real ysagiv root FENs at
  `max_depth = 36` and assert **no node is ever marked terminal by the depth
  cap** — confirming 36 is non-limiting in the live pipeline, matching §2.2.
- Optionally compare to the stored `.pt` to a **tolerance** (WDL/Q within ~5e-3,
  the cross-set agreement from [[tree-set-and-gss]]). Do **not** assert bitwise
  here: the canonical set mixes cuda/blas lanes and we don't control the original
  process, so exact match is neither expected nor required. Bitwise exactness is
  owned by §4.2/§4.3.

### 4.5 Timing / smoke

A `<2 min` smoke that generates a few-tree pool end-to-end, asserts the records
validate, and prints `trees/s` and `evals/s` for ref vs batched so the speedup is
visible in CI logs. No correctness claim beyond "runs and validates."

   tolerance comparison; not needed for Track A correctness.
